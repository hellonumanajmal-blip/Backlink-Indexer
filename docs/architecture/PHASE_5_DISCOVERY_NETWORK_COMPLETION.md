# Phase 5 — Discovery Network Completion

This document describes the final completion stage for Phase 5: the Discovery Network and signal generation architecture.

## Goals
- Complete the discovery signal engine with production-quality feed generation, validation, history, hub publishing, and IndexNow submission.
- Preserve full compliance with search engine guidelines: no fake indexing, no fake traffic, no ranking manipulation, no Google scraping, and no indexing guarantees.
- Maintain backward-compatible APIs and existing module boundaries.
- Provide reliable, append-only history and validation for every generated signal.

## Architecture

The Discovery Network is built as a modular pipeline with separate responsibilities:

- **Feed Engine**: generates RSS, Atom, and JSON Feed from validated discovery items.
- **Validation Engine**: validates every generated feed before it is accepted or published.
- **Feed History**: records generation metadata, checksum, duration, validation status, and trigger metadata.
- **WebSub Publisher**: publishes feed notifications to configured hubs without blocking API requests.
- **Hub Management**: tracks hub health, priority, retry behavior, and delivery metrics.
- **IndexNow Service**: submits only owned domain URLs, with key verification, secure key storage, batching, retry, and duplicate prevention.
- **Signal Timeline**: appends event records for each stage of the discovery flow.
- **Background Workers**: execute feed generation, validation, WebSub delivery, IndexNow submission, and signal recording.

The pipeline is intentionally decoupled: API requests enqueue work, workers do the actual feed generation and distribution, and history tables provide an audit trail.

## Event Flow

Discovery events are append-only records that describe the platform flow:

1. **Feed Generated**
   - Triggered when a discovery campaign/feed is materialized.
   - Includes generation time, checksum, duration, entries, and feed type.
2. **Feed Validated**
   - Triggered after feed validation completes.
   - Stores validation result, errors, and whether the feed passed.
3. **Feed Published**
   - Triggered when a feed is chosen for WebSub publishing.
   - Includes publish trigger, campaign/project, and worker identity.
4. **WebSub Sent**
   - Recorded for each hub attempt.
   - Stores hub URL, status, latency, attempt number, and response details.
5. **WebSub Retry**
   - Recorded when a WebSub publish attempt is retried.
   - Includes backoff and retry count.
6. **WebSub Failed**
   - Recorded when delivery ultimately fails or a hub circuit opens.
7. **IndexNow Submitted**
   - Triggered when a batch of owned URLs is accepted for IndexNow submission.
8. **IndexNow Failed**
   - Recorded when submission fails due to validation, network error, or server response.
9. **Pipeline Finished**
   - Final end-of-job signal that includes overall status, duration, and correlation ID.

## Worker Flow

Workers are independent execution units that survive failures and resume work.

### Feed Worker
- Generates feeds only when source data changes.
- Writes feeds atomically using temporary files and rename semantics.
- Computes checksums and validates deterministic ordering.
- Records a feed history row for each generation.
- Rejects invalid feeds before publishing.

### Validation Worker
- Validates RSS, Atom, and JSON Feed output.
- Checks XML/JSON syntax and encoding.
- Verifies required tags, GUID uniqueness, valid URLs, no invalid characters, and non-empty items.
- Rejects and records invalid feed output.

### WebSub Worker
- Loads active hubs from the database.
- Publishes only validated feeds.
- Uses concurrent delivery with configurable worker count.
- Applies exponential backoff, jitter, and retry limits per hub.
- Uses a circuit breaker per hub to pause unhealthy endpoints.
- Records each attempt and updates hub health metrics.

### IndexNow Worker
- Submits only URLs for verified owned domains.
- Uses secure key storage and may rotate keys.
- Prevents third-party URL submission.
- Batches submissions and retries failed batches.
- Records submission history and response metadata.

### Signal Worker
- Appends pipeline events for feed, validation, publishing, and submission stages.
- Provides an audit trail for every signal generated by the system.

## Feed Lifecycle

### Generation
- The feed engine collects sorted, deduplicated discovery items.
- Builds feeds in three formats: RSS 2.0, Atom, and JSON Feed.
- Uses stable GUIDs and deterministic ordering to avoid spurious changes.
- Writes to temporary files and replaces destination files atomically.

### Validation
- Validates every generated feed before it is accepted.
- Checks for:
  - Well-formed XML / valid JSON encoding
  - Required feed and item tags
  - Valid date fields and timestamps where applicable
  - Unique GUID/ID values
  - Valid item URLs
  - No invalid characters
  - Non-empty item records
- Stores feed validation results and rejects invalid output.

### Incremental Regeneration
- Tracks feed checksums and content metadata.
- Regenerates only when source data or relevant inputs change.
- Logs generation duration, entry count, checksum, and trigger metadata.

## Retry Strategy

### WebSub
- Retry failed publish attempts with exponential backoff.
- Use configurable max retries and timeout per hub.
- Add jitter to minimize thundering retries.
- Record retry count and backoff behavior in history.
- If repeated failures exceed the hub threshold, open the hub circuit and pause delivery.

### IndexNow
- Batch owned URLs and retry failed submissions.
- Handle transient network failures and server error responses.
- Record submission status and failure details.
- Prevent duplicate resend of identical batches.

## Failure Recovery

- Workers must survive exceptions and continue processing other queued jobs.
- Append-only histories preserve failed attempts and error details.
- Circuit breakers prevent repeated failures from increasing load.
- Feed generation uses atomic writes to avoid partial or corrupted files.
- Validation rejects invalid feeds instead of publishing them.
- Database-backed queues and job records allow resuming work after restart.

## Security

- **Encrypt secrets**: IndexNow keys must be stored encrypted at rest and never exposed in API responses.
- **Verify ownership**: Only verified domains may be used for IndexNow submissions.
- **Reject third-party URLs**: IndexNow endpoint must reject any URL not belonging to the verified domain.
- **Audit changes**: All hub and key management actions must be auditable.
- **Separate API and queue work**: Publishing and submission actions are queued, so no API request blocks on external network operations.
- **Limit data exposure**: Feed and history endpoints should return metadata only, not raw secrets or internal keys.

## Performance

- **Parallel publishing**: WebSub worker can publish to multiple hubs concurrently.
- **Batch processing**: IndexNow submissions are batched for efficiency.
- **Atomic updates**: Feed writes use temporary files and rename semantics.
- **Idempotency**: History records and checksums ensure repeated work is safe.
- **Safe retries**: Retry limits, backoff, and circuit breakers prevent overload.
- **Configurable concurrency**: Hub publish count and worker concurrency are tunable.

## Implementation Notes

- Keep the existing `discovery_network` module as the main implementation area.
- Avoid renaming current routes or changing API contracts.
- Use existing shared configuration and queue services.
- Prefer database-backed models and metrics collection already in place.
- Keep the feed engine deterministic and the validation engine strict.
